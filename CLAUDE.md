# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Lychee AI** — a Chrome Extension (Manifest V3) that renders a model-agnostic AI agent chat in Chrome's native side panel. React 18 + Vite 6 + TypeScript (strict), built on the Vercel AI SDK v5. Runs entirely client-side — **there is no backend**; the panel calls the user's configured model endpoint directly. Most providers ride the OpenAI-compatible adapter, but OpenAI (native Responses API) and Anthropic (native Messages API) route through their own adapters — the choice is made per provider by the capability-profile layer (`src/data/providerProfiles.ts`). See `README.md` for the feature-level tour and the file→responsibility architecture map.

The product is "Lychee AI"; the agent calls itself "Lychee" (`DEFAULT_SYSTEM_PROMPT`, `src/data/settings.ts`). Brand red is `#c9304a` (light) / `#f2687e` (dark) — see the `--accent` and `--lychee-*` tokens at the top of `src/ui/styles.css`, whose comment explains why the UI red is a shade deeper than the logo's. Icons ship from `public/icons/`; `assets/` holds repo-only art (full-res mark, 512px store icon, README banner) and is deliberately outside `public/` so it never bloats the extension bundle.

## Source layout

`src/` is grouped by concern — put new files in the matching directory:

- `src/background.ts` — MV3 service worker (the only *file* at `src/` root; a Vite entry point). `src/background/offscreen.ts` is a sibling entry point: the offscreen-document host that runs the background-research state machine (it has no tab access, so its browse steps round-trip back to the SW — see the research invariants).
- `src/ui/` — React side-panel components (`main.tsx` entry) + `styles.css`.
- `src/tools/` — agent tool definitions and the approval gate; `toolDiscovery.ts` holds the pure progressive-disclosure logic (catalog/search/active-set) behind the `ToolSearch`/`GetTool` meta-tools; `pageControl.ts` holds the page-control session, the point-of-no-return classifier, and per-action dispatch; `tabPolicy.ts` is the pure grouping/closing legality layer behind `GroupTabs`/`CloseTabs`.
- `src/agent/` — the AI/agent core: turn loop, the hybrid provider factory (`provider.ts` — dispatches native OpenAI/Anthropic vs the OpenAI-compatible adapter per `providerProfiles.ts`, and injects per-model reasoning effort), memory dreaming, and the runtime vision probe (`vision.ts`, caches whether a model reads images in `chrome.storage.local`).
- `src/data/` — persistence & config: settings (`chrome.storage`), memory + conversations (IndexedDB). Data-model interfaces live beside their store.
- `src/mcp/` — Model Context Protocol: pure config/policy/naming (`config.ts`, tested), the pure rich-content mapper (`content.ts`, tested), the pure MCP Apps bridge protocol (`appBridge.ts`, tested), the panel-resident connection manager (`manager.ts`), the Chrome OAuth provider (`auth.ts`), and the dynamic-tool builder (`tools.ts`).
- `src/exec/` — the sealed code-execution sandbox behind `RunCode` and behind `CreateArtifact`/`UpdateArtifact`'s rendering: `host.ts` (`ExecHost`, the panel-resident singleton — the McpManager analog for this subsystem) owns one hidden `sandbox-exec.html` iframe, booting it lazily and rebuilding it whenever a round-trip wedges; `engine.ts` runs QuickJS (`quickjs-emscripten-core`) under a timeout/memory budget for `RunCode`; `protocol.ts` is the pure, tested message-shape validation (`isExecHostMsg`/`isExecSandboxMsg`) and output-budgeting (`budgetOutcome`) both sides trust; `runtime.ts` is the sandbox-side entry (bundled as a classic IIFE by `vite.sandbox.config.ts`, never the main build) that actually calls the engine and, for `exec:render`, mounts artifact HTML in a nested `srcdoc` iframe. See its own invariant below.
- `src/platform/` — Chrome/DOM utilities: tabs (incl. close/reopen + the undo stash), `tabIndex.ts` (the gist probe + duplicate detection behind `ReadTabs` mode `"gist"`), `tabGroups.ts` (Chrome tab-group shell), `capture.ts` (the *human* camera-button region picker), DOM→image, panel port, time, plus page control's `domIndex.ts` (indexed-DOM registry), `pageActions.ts` (click/type/select/scroll/press/navigate), `presence.ts` (on-page tint/cursor/spotlight overlay + the `NavigateTab` "navigating to…" intent pill), and `marks.ts` (set-of-marks screenshot). The *agent's* own eyes are `regionIndex.ts` (visual-region registry) + `screenshot.ts` (viewport/element/fullpage capture engine). PDFs are a special case — Chrome's plugin viewer has no scriptable DOM, so `pdf.ts` fetches the bytes itself (LRU-cached) and runs them through **two** engines (see the invariant below): text via `pdfEngine.ts`/`pdfWorker.ts` (pdf-inspector WASM), pixels and bookmarks via pdf.js. The pure range/search/budget logic lives in `pdfText.ts` and the Markdown→per-page translation in `pdfExtract.ts` (both tested). It serves both the foreground `ReadPdf` tool and research's `FetchUrl` PDF path, and runs only in page-like contexts (side panel, offscreen host — never the SW). Functions injected via `chrome.scripting.executeScript` (the `inj*`/`build*` functions in these files) run in the page's isolated world with no shared JS state between injections — keep each one fully self-contained (no closures over outer-scope values, no imports); pass everything it needs as `args` and re-find elements via `data-agent-idx` / `data-agent-region`.

## Commands

- `npm run dev` — `vite build --watch --mode development`. Rebuilds `dist/` on change but does **not** hot-reload; after each rebuild you must click the extension's reload button in `chrome://extensions` to pick up changes.
- `npm run build` — `tsc --noEmit && vite build` (type-checks first, fails fast on type errors).
- `npm run typecheck` — `tsc --noEmit`.

Load the extension: `chrome://extensions` → Developer mode → Load unpacked → select `dist/`.

## Verifying a change

There is a growing **Vitest** suite (`npm test`, or `npm run test:watch`) — 104 `*.test.ts` files (~1,100 tests) sitting beside the pure, Chrome-independent modules they cover (tool discovery, provider profiles, screenshot/stitch planning, browse policy, region indexing, math repair, citations, the approval queue, the sandbox CSP, …). Add unit tests for new pure logic. Most of the codebase is Chrome-coupled, though: to confirm a change works end to end, run `npm run build`, reload the unpacked extension in `chrome://extensions`, then open the side panel and exercise the affected flow. The `/verify-extension` skill runs this end to end.

## Architecture invariants

- **Every agent tool must route through the `requestApproval` gate** in `src/tools/tools.ts` before its `execute()` proceeds — this human-in-the-loop card is the security model. New tools go in `createAgentTools()` and must follow it. Two categories are deliberately ungated because they touch no page/network/data: the internal `Checkpoint` control tool (injected in `runAgentTurn`, `src/agent/agent.ts`, never in `createAgentTools`; its only job is to end a turn and hand off state — the human gate for *resuming* is the Continue card), and the disclosure meta-tools `ToolSearch`/`GetTool` (they only list/activate tools; the tool they load still gates on its own call). Chat.tsx shows one approval card at a time, but the AI SDK runs every tool call from one model step concurrently — two gated calls in the same step (two `RunCode`s, `RunCode` + `CreateArtifact`, `RequestPageControl` alongside either) is the default case, not an edge case. `requestApproval` therefore queues each request through `src/ui/approvalQueue.ts`'s `ApprovalQueue` (pure, tested) rather than holding one bare pending-request slot: a second request while the first is outstanding queues behind it instead of overwriting it — an overwritten request's `resolve` would never be called, permanently hanging that tool's `execute()`, its model step, and the whole chat. `front` is what the card renders; `settleFront` resolves the front and reveals whatever's queued behind it; `drainAll` (Stop, chain teardown) resolves everything pending, front included, so nothing is left awaiting a card nobody will ever answer. The policy-driven early-return paths in `requestApproval` (`always`, session-allowed, turn-allowed, all skipped when `once` is set) bypass the queue entirely — they never enqueue at all.
- **Tools are progressively disclosed.** Only an always-on core (`ToolSearch`, `GetTool`, `ReadPage`) is active per step; the model lists the rest via `ToolSearch` and loads them with `GetTool`, which adds to the per-turn `activeNames` set. `runAgentTurn`'s `prepareStep` turns `activeNames` (plus the core, intersected with the turn's real tools) into that step's AI SDK `activeTools`, so only those schemas reach the model. `activeNames` is created once per continuation chain in `runTurnChain` (`src/ui/Chat.tsx`), seeded from context (`@memory`→`SearchMemory`, an open page-control session→the control cluster) and shared across auto-continue cycles; `RequestPageControl` self-expands the cluster on grant. A new tool added to `createAgentTools()` becomes discoverable automatically (the catalog in `src/tools/toolDiscovery.ts` is derived from the filtered ToolSet) — no catalog to hand-maintain. The disclosure protocol reaches every install via the always-appended `TOOL_DISCLOSURE_NOTE` machinery (not the user-editable `settings.systemPrompt`).
- **An unloaded-tool call must self-heal, never dead-end.** Under `activeTools` the SDK rejects a call to a not-yet-loaded tool with `NoSuchToolError` **before `execute()` runs** — so for a gated tool its approval card never appears and the model has no way back (it could never re-ask for page control after a denial). `runAgentTurn`'s `repairToolCall` therefore rewrites a call naming a *real but unloaded* tool into `GetTool({names:[…]})`, loading it so the model's next call reaches `execute()` and its permission card. Tools removed by policy/permission/tab-access are absent from the ToolSet, so they can never be resurrected this way, and genuinely hallucinated names still surface as errors. Keep this property if you change disclosure or the repair hook (`src/agent/agent.test.ts` locks it down).
- **An image can only reach the model through `imageQueue`.** A tool result *cannot* carry an image: the OpenAI-compatible adapter serializes a tool result's `media` part to plain text, so the model never sees it. Perception tools therefore push a `QueuedImage` (`{dataUrl, caption}`, `src/agent/agent.ts`) onto the shared per-turn queue, and `runAgentTurn`'s `prepareStep` drains it into a synthetic `user` message before the next step — the one channel the adapter turns into an `image_url`. **The caption rides with the image and must describe that image**: the queue mixes `ReadPage`'s set-of-marks shot (numbered boxes mapping to `[index]`) with the screenshot tools' plain crops (no boxes at all), and a model told to look for numbered boxes on an unmarked chart will hallucinate them. Never put image data in a tool's *return value* — that lands in model history and is re-sent every step (`GetScreenshot`/`GetElementScreenshot` return a `shotId`; the UI reads the picture from IndexedDB).
- **Two perception registries, deliberately kept apart.** `domIndex.ts` answers "what can I click?" — *interactive* elements, *viewport-only* (you cannot click what you cannot see), addressed `[3]`. `regionIndex.ts` answers "what can I look at?" — charts/figures/tables/media/cards, *whole-document* (you can screenshot below the fold; you scroll to it first), addressed `[r3]`. The distinct `r` sigil is load-bearing: bare integers in both would let the model aim a `ControlPage` click at a `<figure>`, which fails opaquely. Both stamp the DOM (`data-agent-idx` / `data-agent-region`) so a later, separate injection can re-find the node — and a capture must **re-read the element's live rect after scrolling**, since scrolling triggers lazy-load and sticky reflow that invalidate the indexed rect. Both share one definition of "a component" (`SEMANTIC_TAG_SOURCE`, exported from `regionIndex.ts` and passed into `capture.ts`'s injection as an arg). Match it against an **uppercased** `tagName` — SVG elements are XML-cased, so `svg.tagName` is `'svg'`, and comparing the raw value against `'SVG'` silently drops every inline-SVG chart.
- **Screenshots: one artifact for the user, tiles for the model.** `captureVisibleTab` only ever returns the visible viewport of the *active* tab, so anything taller is scroll-and-stitch (`planStitch`/`planTiles` in `src/platform/screenshot.ts` are pure and unit-tested; the Chrome/canvas code is a thin shell over their plan). Sticky/fixed elements are hidden from the *second* slice onward or the header stamps itself into every slice; scroll position, hidden elements and `scroll-behavior` are restored in a `finally`. A tall page goes to the user as one strip but to the model as sequential full-resolution tiles — one downscaled strip would be an illegible smear on exactly the pages where seeing matters. The two screenshot tools — `GetScreenshot` (rendered viewport, `fullPage:true` for the stitched page) and `GetElementScreenshot` (one `[rN]`/selector region) — are **always present**: every capture is saved as a user-facing artifact (rendered by `ShotCard`). The vision probe no longer deletes them; the pure `planShotDelivery` only routes whether the image *also* reaches the model (`send`) or the shot is saved for the user alone with a note that stops a blind model looping (`blind`/`budget`).
- **PDFs run on two engines, split by what each can actually do.** TEXT comes from **pdf-inspector** (Rust/`lopdf` compiled to WASM, `@firecrawl/pdf-inspector-wasm`), which does position-aware extraction with multi-column reading order, table detection and Markdown conversion — measured ~10x faster than the pdf.js text walk it replaced (218 ms vs seconds for a 75-page paper) and structurally far better, since pdf.js could only join text items with spaces, which shredded two-column papers and tables. PIXELS come from **pdf.js**, which stays because pdf-inspector has **no rasterizer**: `ReadPdf` mode:`"view"`, the PDF `HighlightContent` path and the attachment vision ladder all need a rendered page, and the bookmark outline + `author` are likewise pdf.js-only. Deleting pdf.js would delete those *and* make scanned PDFs unreadable (no text layer AND no image path) — pointedly against the grain of pdf-inspector's own `pagesNeedingOcr`, which names exactly the pages needing eyes. So pdf.js is dynamically imported **only** on those paths; a text-only read never pays for it. One `CacheEntry` per document holds `{bytes, loaded, render?, meta?}`: retaining `bytes` is what lets rendering be lazy and stops `HighlightContent` (find the page by text, then render it) from fetching twice — and every hand-off to pdf.js must be a **copy** (`bytes.slice()`), because pdf.js transfers and detaches what it is given while the cache needs those bytes again. `planEviction` is unchanged and still guards the refcount, since `render` is the only destroyable resource. Extraction is **synchronous** once the WASM is initialized, so it runs off-thread in `pdfWorker.ts` (a Vite entry, spawned by extension URL) behind `pdfEngine.ts` — the `ExecHost` analog, FIFO-queued for the same reason: one single-threaded realm, so a queued call's timeout clock should start when it actually begins. Unlike `src/exec/`'s sandbox, this worker is same-origin and fetches the WASM by URL rather than being handed transferred bytes. **Markdown is not plain text**, and that is load-bearing: emphasis lands mid-phrase (`**Encoder:** The encoder…`), so a literal search for a passage a reader sees would miss. `PageText` therefore carries both `text` (Markdown → the model) and `plain` (stripped → matching); `searchPages` matches *and snippets* on `plain` so the model never receives a snippet it cannot quote back, and `renderPdfPageHighlighted` runs `stripMarkdown(query)` before matching, because the model quotes what `ReadPdf` served it. `stripMarkdown` is deliberately conservative — it declines unpairable interleaved emphasis inside inline math rather than corrupting a formula.
- **`chrome.sidePanel.open()` must be called synchronously** inside the user-gesture handler in `src/background.ts` — no `await` before it, or the browser rejects the call. Chrome has no `sidePanel.close()`; closing is faked by messaging the open panel (named `Port` `"sidepanel"`) to `window.close()` itself.
- **No `.env` / build-time secrets.** API keys are entered at runtime via the Onboarding/Settings UI and stored in `chrome.storage.local`. `host_permissions: ["<all_urls>"]` is what exempts the direct API calls from CORS, so no proxy is needed. (Anthropic's native API additionally needs the `anthropic-dangerous-direct-browser-access` header to accept the extension origin — set in `createModel`.)
- **One capability profile per provider `kind` drives reasoning + adapter choice.** `src/data/providerProfiles.ts` (pure, unit-tested, no Chrome/AI-SDK imports — keep it that way) encodes, per `kind` (openai/anthropic/openrouter/groq/ollama/lmstudio/custom): which adapter `createModel` builds, how a reasoning effort maps to that provider's wire format, the id patterns that mark a reasoning model, the effort rungs the picker's slider offers, and the model-list endpoint. It exists to enforce two hard constraints the research nailed down: OpenAI reasoning **and** function tools only coexist on the **Responses API** (chat-completions 400s that pair — so `kind:'openai'` uses the native adapter, not the compat one), and Groq needs `reasoning_format:'parsed'` whenever tools ride along or it 400s. Reasoning effort is stored per provider (`reasoningEffort`, the default) and per model (`modelConfigs[id]`), resolved by `resolveReasoningEffort` (per-model wins); the slider that sets it lives in the model picker (`src/ui/ModelPicker.tsx`), shown only for reasoning models (auto-detected, manually overridable). `createModel` injects reasoning two ways — native adapters via `providerOptions` middleware, compatible ones via a request-body transform (`reasoningBodyTransform`).
- **Memory & dreaming** (`src/data/memory.ts`, `src/agent/dream.ts`) is timing-dependent: a `chrome.alarms` tick consolidates memories once the user-chosen interval (`dreamIntervalMs`, default 24h; `resolveDreamIntervalMs`) has elapsed *and* only after 30+ min of user inactivity (the idle guard is fixed, not configurable). The alarm period adapts to the interval — `background.ts` reschedules it to `min(interval, 60min)` on install/startup and whenever settings change — so a 30-min choice is genuinely honoured. Dreaming uses `getDreamProvider` (the `dreamModel` pick, else the chat model), and the Memory panel's "Dream now" / "Reset memory" call `runDream()` / `clearMemory()` directly, bypassing both gates. Dream state (`lastDreamAt`/`lastSummary`) lives in `chrome.storage.local` but its get/set/**clear** helpers sit in `memory.ts` so `clearMemory()` resets it in one call. A third, additive protection sits underneath both gates: `runDream` (the one function both the alarm and "Dream now" ultimately call) is guarded by a reentrancy mutex, because dream.ts runs in two JS realms sharing no in-memory state — the service worker's alarm and the panel's "Dream now" — and the service worker can be killed and restarted by MV3 mid-dream. An in-memory flag would guard neither case, so the lock (`acquireDreamLock`/`releaseDreamLock` in `dream.ts`, dumb get/set/clear storage primitives in `memory.ts` alongside `DreamState`) lives in `chrome.storage.local` too: write a token, re-read to catch a same-tick collision (the same accepted one-microtask race window as `settings.ts`'s secret migration), and a lock older than its TTL (or timestamped implausibly in the future, per the same clock-skew tolerance `evaluateDreamDue` uses) is stale and reclaimable. Keep this in mind when reasoning about memory correctness.
- **Page control has two nested gates.** `RequestPageControl` opens a per-task `ControlSession` through the `PageControlGate` (`requestSession`/`session`/`endSession`, implemented in `src/ui/Chat.tsx`, typed in `src/tools/tools.ts`); once a session is granted, individual `ControlPage` steps still route back through `requestApproval` a second time when `isPointOfNoReturn()` (`src/tools/pageControl.ts`) flags them — form submits, cross-origin navigation, Enter keypresses, sensitive fields — each as a one-shot card (no "Allow this chat"). `AutofillForm` rides the same session (it's disclosed in the control cluster on grant): it types the user's saved `profile` memories into the fields you map by `[index]`, but a sensitive field (password/payment) still raises a one-shot point-of-no-return card, submit is never part of the tool, and a cross-origin drift mid-fill ends the session for safety. The on-page presence overlay (`src/platform/presence.ts`) and the session must always be torn down in the continuation chain's **outer** `finally` (`runTurnChain` in `src/ui/Chat.tsx`, alongside `pageControl.endSession()`) — not per `runAgentTurn` — so they survive seamless auto-continues but are always cleared on completion, error, Stop, or the ask-boundary; tearing down only on the success path leaves a stale tint/cursor.
- **Tab organizing has one hard cost rule and one honesty rule.** The agent's view of the window is `buildTabIndex` (`src/platform/tabIndex.ts`) — `ReadTabs` mode `"gist"` — which injects a ~180-char page self-description per tab so the chat model can cluster sixty tabs for ~10k characters instead of reading sixty pages. **A discarded tab is never probed**: `chrome.scripting.executeScript` *wakes* one, so probing a sleeping window would reload every tab at once and spike the RAM Chrome just reclaimed. `planTabProbe` (pure, tested) decides eligibility *before* any injection and hands back a stated `skipped` reason, so the model still sees the tab. The mutation tools (`GroupTabs`, `CloseTabs`) never act on what the model asked for directly: the pure planners in `src/tools/tabPolicy.ts` re-read live tab facts and rewrite the proposal into what is legal — ungrouped-only, split per window (Chrome cannot group across windows, and moving tabs between them is near-impossible to undo), never the active/pinned/last-in-window tab — and everything dropped comes back as `rejected` with a reason. That rewrite is what lets the approval card *itemize the real tabs* (`ApprovalRequest.items`); a card saying "Close 23 tabs" without naming them is not consent. `CloseTabs` is `once: true` (no "Allow this chat" for a destructive batch) and stashes closed tabs for a one-level `reopen`. `tabGroups` is an **optional** permission — Chrome warns on it, so requiring it would disable the extension for existing users on update — and is requested from inside the card's Allow click, which is the user gesture `chrome.permissions.request` needs; keep that call ahead of every `await` in `settleApproval` or the gesture is spent. All three tools are deleted in `active-tab` mode.
- **Long-horizon turns are a continuation chain.** `runTurnChain` (`src/ui/Chat.tsx`) loops `runAgentTurn` under a single 24-step budget (`MAX_STEPS`, `src/agent/agent.ts`) that bounds *all* activity — page control included; there is no separate per-session action budget. Near the ceiling, `prepareStep` nudges the model to call the ungated `Checkpoint` tool, which ends the turn with a structured hand-off (`stop.reason === 'checkpoint'`; a hard cut-off is `'budget'`). The foreground chain auto-continues up to `MAX_AUTO_CONTINUES` — the session/overlay persist across these — then surfaces the Continue card. Auto-continue only refreshes the *step* budget; point-of-no-return steps still confirm individually every time.
- **The user can steer a turn mid-flight.** While a chain is streaming, a composer submit is *not* a new turn — `steer()` (`src/ui/Chat.tsx`) assembles it as an ordinary user message and pushes it onto `steerQueueRef`, a by-ref array of *promises* (so `steerPending` flips true synchronously even while the steer is still resolving its attached-tab context, and no steer is dropped at a cycle boundary). `runAgentTurn` takes one option, `steerPending?: () => boolean`, OR'd into `stopWhen` beside `isStepCount`/`hasToolCall(Checkpoint)`: the loop halts at the next **step boundary** — never mid-token, never mid-tool, and during page control never mid-click, so a steer can't jump an open approval gate. `runTurnChain`'s per-cycle drain splices each queued steer into `historyRef` as a real user bubble, opens a fresh assistant bubble beneath it, and continues on a **fresh step budget that is not charged against `MAX_AUTO_CONTINUES`** (it's user-driven, not an auto-continue). A steer's screenshot/tab attachments ride the ordinary user-history path, *not* `imageQueue` (a user message may carry an image part; a tool result may not — see the image invariant). Steering is foreground-only (background research has no user); `stop()` and the chain's outer `finally` clear the queue, so Stop discards pending steers, and a leading `/skill` is honored only for a fresh turn, never a steer. `src/agent/agent.test.ts` locks the `steerPending` stop-condition down.
- **Background research is a phased pipeline, not a flat loop.** `runResearch` (`src/agent/research.ts`, in the offscreen host) is a state machine — Scope&Plan → (Gather ↔ Reflect, bounded by `MAX_GATHER_ROUNDS`) → Synthesize → Verify — over a structured `ResearchNotebook` (`src/agent/notebook.ts`: plan, sources, findings, images, coverage) that is the long-horizon memory; each gather round is a fresh `runAgentTurn` seeded from a notebook *summary* (not a growing history) and can `Checkpoint` internally. Its tools (`createResearchTools`, `src/tools/research.ts`: WebSearch, FetchUrl, BrowseSite, ExtractDataText, ExtractTable, SearchAcademic/SearchImages/HarvestImages (backed by `src/platform/researchSources.ts`), ReadNotebook/WriteNotebook) are ungated (no user is present) and **all-active** (the research loop doesn't use `runTurnChain`'s progressive disclosure). Every tool name on this surface must match `^[a-zA-Z0-9_-]{1,64}$` — providers 400 the *whole* request over one bad name, and since research retries transient failures it would then retry to its 24h deadline without ever reaching the model (`src/tools/toolNames.test.ts`). The report cites sources as `[[n]]` sentinels that render as inline favicon chips (`src/ui/citations.ts` + `Markdown`).
- **MCP is panel-resident, and its config IS the standard file.** The `McpManager` singleton (`src/mcp/manager.ts`) lives in the side-panel context only — never the MV3 service worker (its lifetime kills SSE streams) and never the research pipeline (MCP is foreground-only; no human would gate the calls). `Settings.mcp.servers` is byte-for-byte the standard `mcpServers` JSON object, so upload/edit/copy in Settings → General are pure serialization; extension-private state rides sidecar maps (`serverState`, `policies`) and OAuth tokens live under separate `mcpAuth:<server>` keys — the exported JSON can never leak credentials. stdio entries are preserved verbatim but unrunnable (shown greyed with a bridge hint). MCP tools reach the turn **through `createAgentTools`'s `extraTools` parameter, never spread in by the caller**: the disclosure catalog is derived from that ToolSet, so a tool merged outside it could not be listed by ToolSearch, loaded by GetTool, or rescued by the repair hook. Each MCP tool's `execute()` gates on `requestApproval` under the two-level policy (per-tool override → server default → `ask`, `src/mcp/config.ts`); `never` at either level means the tool is not built at all. Rich results are split by the pure mapper `src/mcp/content.ts` — model text (budgeted), images via `imageQueue` (the image invariant holds for MCP; a blind model gets a note instead), everything else as artifact cards in the `lychee-mcp` IndexedDB. OAuth (`src/mcp/auth.ts`) implements the SDK's `OAuthClientProvider` over `chrome.identity.launchWebAuthFlow`; an interactive popup may only ever launch from an explicit user click (Authorize buttons) — a background reconnect gets a non-interactive provider that refuses, parking the server at `needs-auth`. MCP Apps run their HTML in `public/sandbox.html`, a manifest-sandboxed page (unique origin, no `chrome.*`) whose script is deliberately an **inline classic script** — a sandboxed page's opaque origin fails CORS on module-script fetches — and every in-app request is decided by the pure bridge (`src/mcp/appBridge.ts`) in the panel: tool calls re-enter the same policy + approval gate, scoped to the app's own server. An app card can act after its own turn is over (a button click, a status poll), so the host actions it needs (`callTool`, `draftMessage`) are registered per-conversation in `src/ui/mcpAppHostRegistry.ts` — keyed by `conversationId`, never a single shared slot. The panel deliberately keeps a background conversation mounted alongside the visible one (`tabChats.ts`'s `liveChatIds`), so more than one conversation can be registering host actions at once; a shared slot would let one conversation's app card be serviced by whichever *other* conversation's Chat last rendered — its "Allow this chat" grants, its session-allow set — a cross-conversation approval bypass. The registration cleanup only removes an entry if it's still the one that call installed, so an out-of-order unmount can never delete a newer registration for the same conversation.
- **The research agent browses through one leased, isolated tab, and a policy — not a human — is its gate.** Three tab consumers lease it from `src/platform/researchTab.ts` (incognito when allowed, minimized, mutex'd, idle-torn-down, orphan-swept on SW restart): the *passive* one-shot render (`researchRender.ts`, auto-escalation for a thin/failed `FetchUrl`), the *active* browse session (`researchBrowse.ts`, driven by the `BrowseSite` tool), and the *search fallback* (`researchSearch.ts`). The keyless DuckDuckGo fetch (`webFetch.ts`) is frequently bot-throttled (202/429 — a plain `fetch()` can't set `User-Agent` and carries a `chrome-extension` `Origin`, so it can't clear the wall); when it fails, `WebSearch` retries the query in a real tab that renders a genuine SERP and scrapes it (`parseDuckDuckGoHtml`/`Lite`, pure + tested). Escalation is transparent to the model — it just gets results. A session holds its lease for its whole life, so a concurrent render can't navigate the page out from under it. `BrowseSite` runs a **nested sub-agent** (`src/agent/browseAgent.ts`) in its own context — the page walk's dozen element registries never enter the gather agent's history — which writes findings straight into the shared notebook and returns a digest. Because the offscreen host can't touch tabs, every step is a `research.browse` round-trip to the SW. **Every action is checked by the pure policy in `src/tools/browsePolicy.ts` before the page is touched**: read + navigate (SSRF-guarded, cross-origin allowed) + site-search only — never a login, purchase, or non-search form submit. That policy is the whole security model here, so it is exhaustively unit-tested (`browsePolicy.test.ts`); keep it pure and keep it that way.
- **The `RunCode`/artifact sandbox is a manifest-sandboxed page with a default-deny CSP, and one call runs at a time.** `src/exec/` (host.ts in the panel, runtime.ts in the sandbox) exists so untrusted code — a model-written `RunCode` script, or model-authored `CreateArtifact`/`UpdateArtifact` HTML — never runs with the extension's own privileges. `public/sandbox-exec.html` is declared in `manifest.json`'s `sandbox.pages` (unique origin, no `chrome.*`) with `default-src 'none'`; every other allowance is deliberately narrow and independently justified, because an unset CSP directive is unrestricted unless `default-src` covers it, and `form-action` specifically does **not** fall back to `default-src` — `script-src 'self' 'unsafe-inline'` (the sandbox's own bundled script, plus inline `<script>` in model-authored artifact HTML — the whole point of `CreateArtifact`), `style-src 'unsafe-inline'`, `img-src data:` (no remote host), `form-action 'none'` (a form renders but can never submit anywhere). Confirmed against a real Chromium instance that a remote `<script src>`/`<img src>`/cross-origin `<form>` are all blocked before they reach the network; `sandboxCsp.test.ts` parses the actual meta tag into a directive map (not a substring check) so a future edit can't silently widen one directive while an unrelated `'none'` substring elsewhere looks reassuring. `CreateArtifact`'s HTML itself renders in a *nested* `srcdoc` iframe inside the sandbox (`sandbox="allow-scripts allow-forms"`, never `allow-same-origin`) — the outer page's CSP is what a `srcdoc` document inherits, so the artifact is doubly contained. `ExecHost.run()` gates every `RunCode` call through a strict FIFO (`runQueue`): the sandbox is one JS realm and QuickJS's `evalCode` is synchronous, so it can never truly service two calls at once regardless, but queuing explicitly means a call's timeout clock starts when it actually begins (not while merely waiting its turn) and means a wedged round-trip only ever has one real in-flight request to collaterally reject when the frame is torn down and rebuilt.
- **The `conversations` `summaries` store is written in the same transaction as the full record.** `src/data/conversations.ts` keeps a second, lightweight `summaries` object store mirroring the history dropdown's handful of scalar fields (title, timestamps, message count, pinned, a byte estimate) for every conversation; `listConversations`/`conversationsUsage` read *only* this store instead of `getAll()`-ing and deserializing every full transcript just to project a few fields — a cost that used to scale with an install's entire lifetime of chat data and was paid on every turn. `mutate()` (the single choke-point behind `saveConversation`/`renameConversation`/`togglePin`) opens one `readwrite` transaction over both `[STORE, SUMMARY_STORE]` and `put`s to both inside it, and `deleteConversation`/`clearConversations` do the same for delete/clear — never two separate transactions. This isn't just an optimization detail: IndexedDB serializes overlapping readwrite transactions on a store, so keeping both halves in one transaction is what makes a read-modify-write (the auto-namer setting a title, a turn saving a fresh transcript) atomic — two separate transactions could interleave into a lost update, and a summary write that ever fell out of the same transaction as its record would drift from it or leave a phantom row after a delete.
- **Secrets are sealed at rest.** Every secret in `chrome.storage.local` — provider `apiKey`s, Langfuse keys, MCP OAuth tokens (`mcpAuth:*`), MCP `headers` values — is envelope-encrypted by the vault (`src/data/vault.ts`): a non-extractable AES-KW KEK in IndexedDB (`lychee-vault`) wraps an AES-256-GCM DEK, and sealed values are `lysec1.` strings (`src/data/vaultFormat.ts`). The seal/open boundary is `loadSettings`/`saveSettings` (via `settingsVault.ts`) plus `mcp/auth.ts` — in-memory `Settings` are always plaintext (one deliberate exception: during a transient vault outage, already-sealed fields pass through still-sealed — re-saving a sealed string is a no-op, whereas resolving to '' would let the next save destroy the ciphertext; loadSettings warns when this happens), so key-reading call sites, the offscreen research handoff, and the MCP JSON export never see sealed values. Never write a secret to storage outside those chokepoints, never persist a secret in any other record (research tasks carry provider config only in runtime messages), and never make the KEK extractable. Vault-down degrades to plaintext writes (availability of the user's own keys beats hygiene); a sealed value that no longer decrypts resolves to `''` and the user re-enters it. Design + threat model: `docs/superpowers/specs/2026-08-01-envelope-encryption-design.md`.
- **User attachments route through the delivery planner.** `planAttachmentDelivery` (`src/agent/attachmentPlan.ts`, pure/tested) is the only place allowed to decide an attachment's wire form: native PDF parts exist only for the two native adapters (`supportsNativeDocuments` in `providerProfiles.ts`), and everything else degrades down a ladder: rendered page images when the vision probe says the model can see, extracted text (via pdf.ts, which accepts raw bytes for exactly this) when it can't. **Do not rely on the OpenAI-compatible adapter to reject a stray PDF for you** — checked against the installed `@ai-sdk/openai-compatible@3.0.7` (`dist/internal/index.js:107-119`), it throws `UnsupportedFunctionalityError` for a non-PDF file part but *silently converts* an `application/pdf` one into OpenAI's proprietary `{type:'file', file:{filename, file_data}}` chat-completions shape. Virtually no non-OpenAI "compatible" backend (Groq/Ollama/LM Studio/generic OpenRouter models) understands that field, so it fails as a 400/422 from the remote server instead of as a local throw — same broken turn, but diagnosed one layer further away. The planner is the guard; the adapter is not. Attachment bytes live once in the capped `lychee-attachments` DB (`src/data/attachments.ts`, screenshots-DB pattern: size+age pruning); persisted history holds `lychee-attachment:<id>` sentinels swapped at the `dehydrateHistory`/`hydrateHistory` boundary (`src/data/attachmentRefs.ts`, the parts are tagged via a `providerOptions.lychee` namespace no adapter reads) — never inline file data in a stored conversation, and a pruned attachment must rehydrate into an explanatory text part, never a broken file part. Ingestion (drop/paste/paperclip → `src/ui/attachments.ts`) validates per file and never aborts the batch; design: `docs/superpowers/specs/2026-08-02-prompt-attachments-design.md`.
- **Observability redaction happens after the gate, not instead of it.** `instrumentToolset` (`src/agent/observability/instrumentTools.ts`) wraps every tool's `execute` so a call becomes a Langfuse span, but a tool-call argument frequently carries a real secret typed through the page — `AutofillForm`'s `fields[].value`, `ControlPage`'s `text`/`value`, the DOM registry's re-read `value`s flowing back out through a tool's own result — and these are generic key names by design (the UI maps arbitrary form fields onto them), so no name-pattern redaction alone catches them. `redactSecrets` (`redact.ts`) therefore runs two independent nets on everything before it reaches a span — NAME-based (a key matching a known sensitive pattern) and SHAPE-based (a string value that is Luhn-valid or high-entropy, regardless of its key name) — plus a narrower rule that redacts a sibling `value`/`text` whenever the same object carries domIndex.ts's own computed `sensitive`/`isSensitive` flag; it fails closed (an internal error redacts rather than risking raw passthrough) and only nukes the cyclic branch on a circular reference, not the whole payload. The span itself is only created *after* `orig()` (the wrapped tool's real `execute`, including its own internal `requestApproval` call) resolves — never before — so a call the user denies never has its real arguments transmitted at all: a denied call's input is replaced with a fixed placeholder outright, not merely redacted-by-pattern, since a denied action has no debugging value that justifies betting on the heuristics being complete.
